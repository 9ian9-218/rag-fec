## 问题定位

### L1. 外部依赖：embedding API 402（根因，非代码问题）
- SiliconFlow 余额不足，所有向量化失败：检索阶段 embedding 重试链（每次请求浪费约
  1~5s）+ 索引写入不可能。**这是 QPS 低与检索全空的第一根因**。

### L2. 链路设计：空检索仍调用 LLM 生成"兜底回复"（可优化）
- 检索为空时链路仍走 `answer_with_retrieved_text_only` 调 LLM（mimo-v2.5 每次
  10~30s），这部分构成未缓存请求的绝大多延迟（遥测 12~40s）。
- 空检索应**直接短路**返回模板化"根据检索材料无足够信息"响应，不再调 LLM
  （plan.md Phase A 的"快速失败/兜底"项未落实）。

### L3. 并发行为：长尾随并发放大（架构信号）
- 并发 8 档 p99=37.3s / max=40.3s：LLM 并发（max_concurrent_calls=8）+ mimo-v2.5
  慢模型 → 慢请求占满信号量后新请求排队。错误率 0 但长尾恶化。

### L4. 缓存：工作良好（收益已验证）
- 重复问题命中 Redis 答案缓存：p50=0.014s、QPS 2.94（并发 8 档大部分命中）。
- 命中缓存的请求不进遥测（预期行为）。缓存 TTL 300s 内压测池复用效果显著。

## 优化意见（按优先级）

| # | 优化 | 预期收益 | 成本/风险 |
| --- | --- | --- | --- |
| P0 | **充值/修复 embedding API**（治本） | 检索恢复，QPS 从 0.3~3 回到几十级 | 外部账户操作 |
| P1 | **空检索短路**：检索无内容时跳过 LLM，直接返回模板化"无足够信息" | 未缓存请求延迟 15~40s → <1s；QPS ×10+ | 低；注意保留遥测与反馈条 |
| P1 | **确定性错误 fail-fast**：embedding 返回 402/403（余额类）不做重试、立即降级 | 每请求省 1~5s 重试链 | 低；retry.py 增加不重试错误码 |
| P2 | LLM 加速：换更快模型 / 流式输出首字体验 / 限制 max_tokens | 生成段延迟降低 | 中；质量权衡 |
| P2 | 问题归一化提高缓存命中（同义问题标准化后查缓存） | 缓存命中率 ↑，平均延迟 ↓ | 中 |
| P3 | 压测脚本增强：`--ramp` 下档间退避已支持；可加"缓存 vs 新问题"分离统计 | 压测可读性 | 低 |

## 结论

- 压测脚本功能正确（预检/分类/报告/拐点均正常），错误率 0，服务稳定无崩溃。
- 当前指标瓶颈不在服务代码：检索全空（embedding 402）→ LLM 兜底生成 15~40s 构成
  全部延迟；缓存命中请求毫秒级返回证明服务本身吞吐上限远高于实测 QPS。
- 修复顺序：先 P0（embedding 可用）验证真实检索链路，再 P1 短路与 fail-fast
  消除 402 环境下的浪费，最后 P2 调优生成与缓存。
